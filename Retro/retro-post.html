Building a 26-Tool Design System Workbench in 3 Hours

How a procedural approach, agent teams, and a Design QA role turned a blank directory into a full design infrastructure toolkit.

Feb 13, 2026 15,936 lines of code 3h 15m wall-clock

Overview

The machine that designs the design.

Most design systems are built as static specs — a Figma file, a handful of Notion pages, a token JSON someone hand-wrote. The Design System Workbench takes a different approach: every design decision is generated procedurally from tunable parameters.

The idea comes from tools like Lyft's Colorbox.io, which generates color palettes from bezier curves rather than manually picking hex values. We applied that philosophy to everything — typography, spacing, shadows, easing curves, grid systems, even voice and tone.

The result: a React + TypeScript web app with 26 interactive tools across 9 design areas, all feeding into a shared token store that exports to CSS custom properties, JSON (W3C DTCG format), and Tailwind config.

Phase 0 — Foundation
Architecture & Core Infrastructure
Token data model (W3C DTCG), Zustand store with undo/redo, OKLCH color engine, bezier solver, spring physics, UI shell with sidebar navigation. Everything the 26 tools would plug into.
Phase 0 — First Tools
Color Lab, Typography Lab, Spacing Lab, Shadow Lab, Easing Curves
The five foundational generators. Color Lab alone has 3 bezier curve editors controlling hue, chroma, and lightness independently in OKLCH space — the Colorbox.io approach applied to the entire color pipeline.
Phase 1 — Solo Build
5 more tools: Duration Scale, Grid System, Contrast Matrix, CVD Simulator, Voice & Tone
The accessibility tools (Contrast Matrix, CVD Simulator) were the first to consume tokens from another tool — they read Color Lab's output in real-time. Change a palette and the N×N contrast grid updates instantly.
Phase 2 — Team Formation
3 Builders + 1 Design QA agent
For the remaining 16 tools, an agent team was created. Three builders worked in parallel across 4 waves, with a Design QA agent reviewing every tool against a 10-point checklist after each wave.
Wave 1 — Tier 1
Iconography, Touch Targets, Focus Order, Microcopy, Breakpoints
Simple, independent tools with no token dependencies. QA found the first systemic issue: hardcoded Tailwind colors instead of CSS variables.
Wave 2 — Tier 2
Chart Palette, Data-Ink, Responsive Spacing, State Machine
Token consumers and the first visual editor (State Machine with draggable SVG nodes). Responsive Spacing was flagged by QA as the cleanest tool — defensive circular-read prevention, proper copy feedback.
Wave 3 — Tier 3
Theme Derivation, Feedback Patterns, Choreography
The most algorithmically complex wave. Theme Derivation inverts OKLCH lightness curves via a bezier editor to generate dark mode. Feedback Patterns sequences animations frame-by-frame using requestAnimationFrame.
Wave 4 — Tier 4
Token Taxonomy, Relationship Graph, Export Pipeline, Theme Comparison
The meta-tools. Taxonomy Builder creates semantic aliases. Relationship Graph renders a force-directed visualization of token references. Export Pipeline connects the whole system to CSS, JSON, and Tailwind output. All 26 tools complete.
Deployment
GitHub + GitHub Pages + Portable Zip
First deploy failed — CI's tsc -b was stricter than local tsc --noEmit. 30+ errors to fix. Then BrowserRouter broke on zip hosting. Switched to HashRouter for universal compatibility.

Key Decisions

The architectural bets and how they paid off.

OKLCH as the Internal Color Space

Every color in the system is stored as OKLCH — lightness, chroma, hue. Not hex, not HSL. This matters because OKLCH is perceptually uniform: a 10-unit change in lightness looks the same regardless of hue. The Color Lab's bezier curves operate on these three channels independently, and the result actually looks evenly spaced. HSL would have produced uneven palettes that "feel wrong" without manual tweaking.

Zustand + Immer + Zundo

The token store is the nervous system of the workbench. Every tool reads from and writes to it. Zustand was chosen over Redux for simplicity — no boilerplate, no action creators, just a store with methods. Immer makes nested token tree updates ergonomic. Zundo adds undo/redo with one line. The store persists to localStorage, so your work survives page refreshes.

W3C DTCG Token Format

The internal data model follows the W3C Design Tokens Community Group specification. Every token has $value, $type, and $extensions. Aliases use {color.blue.500} syntax. This means the export pipeline is nearly trivial — the internal format is the standard format.

HashRouter Over BrowserRouter

BrowserRouter requires server-side redirects to handle client-side routes. It broke on GitHub Pages (needed a 404.html hack) and broke completely on the zip hosting platform (which serves under an unpredictable subpath). HashRouter uses URL fragments (/#/visual/color-lab) that work everywhere without server configuration. Uglier URLs, universal compatibility.

// The one-line change that fixed deployment everywhere
export default function App() {
  return (
    <HashRouter>
      <AppShell />
    </HashRouter>
  );
}

Reflections

What worked, what broke, what we'd change.

The hardcoded color problem was the #1 recurring issue across all 4 waves. Every QA review found it. The fix was always the same. We should have made it impossible, not just inadvisable.

What Worked

Wave-based parallelism with dependency ordering

Independent tools first, consumers second, meta-tools last. Three builders never blocked on each other within a wave. The dependency graph was the execution plan.

The Design QA role

Not just catching bugs — establishing patterns. The QA agent's checklist matured across waves, and its reviews created a feedback loop that improved each subsequent wave's output.

The shared token store as integration bus

Color Lab writes → Contrast Matrix reads → Theme Derivation transforms → Export Pipeline formats. No tool-to-tool coupling. Just the store. Every tool is both independent and interconnected.

What We'd Do Differently

Ban hardcoded colors in builder instructions

Not "use CSS variables" — an explicit banned list: NEVER use text-red-*, bg-white, text-white, or hex values. Make the constraint impossible to miss.

Create shared components earlier

A <CopyButton> component with clipboard + checkmark feedback should have been in Phase 0 shared controls. Instead, every builder reinvented it (or forgot it).

Match CI strictness locally

tsc --noEmit passes locally. tsc -b fails in CI. The gap caused 30+ errors on first deploy. Always run what CI runs.
